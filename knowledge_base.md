## 1. Компания и роль Никиты

**Никита** — CPO в Beetrail, опыт в роли 1 год (текущий уровень ~1.5).

**Beetrail** — аутсорсинговая разработка мобильных приложений (iOS/Android/кроссплатформа). Полный цикл: Discovery → BA → UX/UI → Разработка → QA → Поддержка.

**Стек:** FlutterFlow, Flutter, Firebase, Supabase, Jira, Trello, Figma, Shtab.

**Команда:** CPO (Никита) + PM-ы + BA + UX/UI-дизайнеры + QA + разработчики (FlutterFlow).

**Пороги входа:** СНГ — от $25k, Западные рынки — от $70k.

**Важная техническая особенность:** FlutterFlow-проекты — нельзя упоминать FlutterFlow при публикации в сторах, нужно регистрировать домен (иначе светится адрес платформы).

**Что Никита делает ежедневно (факт, не по описанию должности):**
- Общение с клиентами на уровне подписания документов и актов выполненных работ
- Выбивание оплат от клиентов
- Общение с PR-менеджерами
- Коммуникация с разработчиками по зарплатам и включению в проекты
- Обсуждение с CTO ключевых технических тонкостей
- Разговоры с клиентами о постпроектных задачах (мониторинг метрик, сервисы)

**Главная проблема компании:** размытое позиционирование («полный цикл разработки») + отсутствие собственных кейсов с цифрами.

**Конкурентное преимущество:** AI-ускорение BA — 480ч → 158ч (задокументировано). FlutterFlow: скорость разработки. Выстроенные процессы и финансовая дисциплина.

**Текущий портфель (май 2026):**
- Клиент 1: завершение разработки, проблема с выпуском в App Store / Google Play, начат разговор о постпроектной поддержке
- Клиент 2: активная разработка
- Клиент 3: T&M (Time & Materials) — стабильный, самый ценный по LTV и потенциалу допродаж

**Стратегические идеи Никиты:**
- Новое позиционирование: «Помогаем проверить идею до того, как вы потратите $100k»
- Трёхуровневая линейка: Express Discovery → Быстрый MVP → Полный цикл
- Сегментация: стартапы (валидация) vs. действующий бизнес (рост метрик)
- Vibe-coding для быстрых и дешёвых MVP
- Помощь с публикацией в сторах как отдельная платная услуга

## 2. Уровни CPO и план перехода 1.5 → 2 → 3

### Уровень 1 — Проектный супервайзер (ставка)
Глубокое погружение в операционку. CPO = первая точка эскалации. CEO не вмешивается в рутину.

**Ключевое:** ежедневный контроль всех проектов, прямое управление PM-ами, разрешение конфликтов с клиентами, контроль доп. работ и счетов.

**Критерий успеха:** CEO не приходится вмешиваться. Все доп. работы посчитаны и согласованы. Проекты ведутся по стандартам.

### Уровень 2 — Руководитель производства (повышенная ставка)
Управление через систему, а не напрямую. Меньше в чатах — больше в построении процессов.

**Ключевое:** управление через PM-ов, владение P&L каждого проекта, проактивные допродажи, CSAT/NPS, бюджетирование, развитие команды PM-ов, участие в пресейле.

**Критерий успеха:** выполнение плана по маржинальности и допродажам. Высокие CSAT/NPS. Сильная самостоятельная команда PM-ов.

### Уровень 3 — CPO (ставка + % от чистой прибыли)
Стратегический партнёр CEO. Управляет производственным юнитом как отдельным бизнесом.

**Ключевое:** полная ответственность за P&L производственного департамента, стратегическое планирование ресурсов, право вето на рискованные проекты, удержание и развитие ключевых клиентов, запуск новых услуг, система грейдов и мотивации команды.

**Критерий успеха:** чистая прибыль департамента, LTV клиентов, низкая текучесть кадров, успешный запуск новых сервисов.

### Чеклист перехода на Уровень 2 (ключевые задачи)

| Действие | KPI / критерий |
|---|---|
| Единый дашборд всех проектов в Trello | 100% проектов в Trello, обновление еженедельно |
| Правило «вне ТЗ → оценка + доп.соглашение» | 100% запросов вне ТЗ — через процесс |
| Еженедельные 1:1 с каждым PM (30 мин) | ≥90% 1:1 проведены, блок upsell в каждом |
| Внедрить CSAT/NPS после каждого этапа | Минимум 1 опрос на проект |
| Собрать бэклог доппродаж по каждому клиенту | 5–10 идей допценности на клиента |
| CR-light для изменений скоупа | 100% внеплановых задач оформлены CR |
| Upsell pipeline (идея → оценка → согласование → оплачено) | Обновление еженедельно |
| Подготовить кейс для CEO о повышении | Презентация: метрики + достижения + план |

## 3. Клиенты и портфель

**Идеальный клиент (ICP):** Founder/CEO/Owner (или группа ЛПР), хорошо разбирается в своём бизнесе/рынке, хочет решить конкретную проблему через цифровой продукт. Может не разбираться в IT — важно, что принимает управленческие решения исходя из бизнес-целей.

**Обязательное условие:** один контакт — owner of communication, который ведёт ежедневную коммуникацию и приёмку.

**Скоринг лида (0–100):** 80–100 — приоритет; 60–79 — брать с фиксацией рисков; <60 — скорее не наш клиент.

**Ключевой параметр скоринга (0–15):** финансовая дисциплина. 15: готов к предоплате/чёткому графику; 8: только постоплата при ясных условиях; 0: уклоняется/торгуется агрессивно.

**Жёсткие дисквалификаторы (не берём):**
- Gambling/казино
- Отказ от Discovery; «давайте сразу кодить»
- Отказ от QA/тестирования
- Отказ фиксировать решения письменно и признавать Change Request
- Бюджет сильно ниже порога без готовности сузить скоуп
- Токсичная коммуникация на старте: грубость, угрозы, ультиматумы

**Красные флаги (2–3 одновременно = высокий риск):**
- Агрессивный торг и фокус на «самый дешёвый вариант»
- Нереалистичные сроки без готовности к компромиссам
- Нет дисциплины приёмки
- Продавливание границ: требования вне договора
- Ночные/выходные как норма

**Если «надо взять» с красными флагами — обязательные условия защиты:**
- Только через обязательный Discovery и утверждение артефактов
- Жёсткий Change Request на любые изменения
- T&M, более частый биллинг (раз в 2 недели), предоплаты за этапы
- Политика гарантии: ориентир 60 дней по дефектам (без «бесконечной бесплатной гарантии»)

## 4. Допродажи — методология и скрипты

### Внутренняя установка (MindSet)
- «Дорого» — миф. Не решай за клиента, есть ли у него деньги. Задача — показать, как решение окупится.
- Партнёрство на равных. Не обслуживающий персонал — эксперты. Не заискивай.
- Скидки только в обмен на уступку: сокращение объёма, предоплата 100%, отзыв или кейс.
- Клиент платит лично (ЛПР). Решай его личные боли: спокойствие, статус «героя» в компании.
- Невыставленный счёт не может быть оплачен. Больше счетов = больше денег.

### Подготовка перед контактом
- Изучить соцсети и публичные выступления ЛПР
- Понять нишу, продукт и как на нём зарабатывает клиент
- Найти триггеры «геройства»: как допродажа сделает клиента крутым в глазах руководства
- Подготовить релевантный кейс
- Найти «мосты» — общее (хобби, география, знакомые)

### Коммуникация
- Слушай больше, говори точнее. Клиент сам расскажет о болях, если не мешать.
- Сочувствие ≠ Ответственность. Не становись «покупателем чужих проблем».
- Метод «Дай попробовать»: вместо продажи большого этапа — продай 8 часов аналитики или преддискавери. Дай «потрогать» артефакты.

### Результат и дисциплина
- Добивайся конкретного решения («Да/Нет/Срок»), а не просто «мы поговорили».
- В конце дня: «Всё ли я сделал сегодня для достижения цели?»
- Говорить языком пользы, а не технологий: не «добавим AI-ассистента», а «сократим нагрузку на саппорт и ускорим ответы пользователям».

### Основной мотив клиента — быть героем
Продавать допы как способ: снять риски, дать быстрый результат, усилить позицию клиента внутри компании.

## 5. ICP — кто идеальный клиент Beetrail

**Ожидания от клиента (операционная совместимость):**
1. Не затягивает приёмку этапов; даёт обратную связь в разумные сроки
2. Работает от договора и фиксированных договорённостей; изменения — через Change Request
3. Своевременные выплаты по факту приёмки
4. Не обесценивает работу постфактум
5. Не продавливает границы и не требует работы вне согласованного объёма
6. Уважает рабочее время команды
7. Активен в обсуждениях: регулярно на связи и принимает решения
8. Обеспечивает базовые доступы/аккаунты без недельных задержек

**Типичный продуктовый контур:** приложение + админка/кабинеты + backend + интеграции.

**Техническая грамотность:** клиент не обязан быть технарём. Важно — принимает процесс и не ломает базовые практики качества.

## 6. Управление PM-ами и командой

### Роль PM
PM = главный координатор. Переводит бизнес-требования в конкретные задачи, контролирует выполнение, своевременно реагирует на отклонения.

**Ключевые обязанности PM:**
- Управление сроками и этапами — планирование, контроль дорожной карты
- Финансово-договорная часть — инициировать доп.соглашения при изменении scope
- Коммуникации — вести клиента, информировать CPO и команду, еженедельные отчёты
- Контроль команды — ежедневные синки, баланс загрузки

**Чек-лист PM (обязательное):**
- Принято и проверено ТЗ от BA
- Бэклог создан и актуален
- Сервисы подключены вовремя
- Регулярные синки проведены
- Все блокеры эскалированы своевременно
- Еженедельный отчёт CPO отправлен
- Доп. соглашения инициированы при scope changes
- Проведена ретроспектива с командой

**Формат еженедельного отчёта PM для CPO:**
- Статус проекта — укладываемся ли в срок
- Сделано за неделю
- В процессе — задачи текущей недели
- Риски/блокеры + решения
- Решения, где требуется помощь CPO

**PM Scorecard (4 показателя для оценки PM):**
1. Сроки/предсказуемость
2. Маржа/часы
3. Коммуникация с клиентом
4. Качество планирования (меню + CR)

### Мотивация PM на допсоглашения
За успешную продажу и реализацию допов — материальное вознаграждение и премии. PM заинтересован не только защитить проект, но и проактивно искать точки роста через допы.

## 7. Процессы: запуск проекта, T&M, допсоглашения

### Запуск проекта (чек-лист CPO)
1. До подписания договора: создать/передать карточку проекта в Trello; зафиксировать финансы и состав команды
2. После заключения договора: провести кик-офф и вводную для команды
3. Организовать рабочие инструменты (планирование)
4. Организовать отчётность и коммуникации
5. Контроль и сопровождение проекта (документацию клиенту отправляет CPO)
6. Завершение: отправить акты, провести ретроспективу, зафиксировать выводы

### T&M (Time & Materials)
Под каждый проект согласовываются свои условия работы по T&M. Общий концепт:
1. Формируется «Заказ» за отчётный период (месяц/спринт)
2. Перед началом периода с заказчиком согласуется перечень работ
3. После выполнения — предоставляется отчёт
4. Процесс: формируется бэклог → описание задач → приблизительная оценка командой → информирование заказчика → согласование приоритетов → выполнение → демо → счёт
5. Выставление счёта: по итогам двухнедельного спринта или месячного периода

### Допсоглашения (ДС) — инструкция для PM

**Принципы:**
- Любое новое требование сравнить с исходным объёмом: если входит — делаем в рамках; если нет — оформляем как ДС
- Не оставлять изменения на словах — фиксировать письменно
- Правило треугольника: объём–сроки–стоимость. При новых требованиях что-то из трёх меняется
- Не начинать работу по допу до согласования (минимум письменное подтверждение)

**Категории ДС:**
1. По инициативе клиента (новые фичи, переработка, новые платформы)
2. По инициативе PM/команды (экспертные улучшения: AI-бот саппорта, UX-узкие места, инфраструктура)

**Алгоритм PM при запросе клиента:**
1. Зафиксировать запрос письменно
2. Проверить — входит ли в исходный scope
3. Запросить оценку трудозатрат у команды + влияние на сроки
4. Сформировать для клиента понятное описание, стоимость, изменение сроков
5. Предложить варианты (минимальный / оптимальный / расширенный)
6. Передать на юридическое оформление (СРО)

**Структура ДС:** предмет допа + объём работ + сроки + критерии приёмки.

**Мини-чек-лист PM по ДС:**
- Запрос зафиксирован письменно
- Проверено: входит или нет в scope
- Получена оценка команды
- Подготовлено простое объяснение для клиента
- Обсуждено с клиентом, получено согласие
- Передано на оформление (СРО)
- Работы по допу не стартовали до согласования
- Доп включён в план проекта

### Особенности мобильной разработки (контрольные точки)
- Обязательное 14-дневное тестирование в Google Play (закрытый или открытый тест)
- Заранее учитывать задержки App Store/Google Play review (несколько дней/недель)
- Регулярно напоминать клиенту о регистрации внешних сервисов (занимает недели)
- Для РФ — требования 152-ФЗ о персональных данных, российские серверы
- Демо для клиента: после основной функциональности, перед внешним тестированием, перед релизом
- Различать технический релиз в стор и маркетинговый запуск

### Передача артефактов клиенту (при завершении проекта)
**Ключевые технические файлы (мобайл):**
- App Store: AuthKey_*.p8 (для App Store Connect API), APN.p8 (push-уведомления)
- Google Play: service-account.json, хранилище ключей (upload keystore — хранить даже если Google переподписывает)
- Документация в репозитории: архитектурный обзор, как развернуть, какие сервисы используются, где хранятся ключи/доступы (сами секреты не в репо)

**Политика доступов:** разработчикам не выдавать полный доступ к аккаунтам заказчика. Приглашать с нужными правами (App Store Connect: Users and Access; Google Play Console: Users and permissions).

## 8. Стратегические инсайты (из курсов и книг)

### Из курса по стратегии (тезисы)
- Выбор сегмента = выбор Jobs-to-be-Done: какую «работу» клиента/пользователя делаем лучше конкурентов
- Time-to-market — часть «как выигрываем»: скорость принятия решений + скорость и предсказуемость поставки
- Принцип DRI (Directly Responsible Individual): у каждого стратегического пункта должен быть один владелец — без этого delivery почти не происходит
- Отсутствие продаж — сигнал ошибки в выборе пути (ICP/позиционирование/канал/оффер), а не только в деталях реализации
- Стратегия — непрерывный процесс: ежемесячный health-check + полугодовой пересмотр
- Нужны отказные правила в пресейле (что не берём), иначе стратегия распадается и маржа деградирует

**90-дневный план улучшений:**
- Определить 1–2 ICP и 1 главную ставку How to win (Vibe-coding + валидация гипотез)
- Еженедельный разбор pipeline по ICP: причины «не покупают», корректировки оффера
- Системный разбор отказов: не просто фиксировать «не купили», а находить повторяющиеся причины (дорого / долго / непонятно / нет доверия / нет кейсов)
- Упаковать ценность в офферы, а не в этапы: не «дискавери + полный цикл», а «проверим идею за 2 недели» / «MVP за 4–6 недель» / «найдём где теряете пользователей»

### Из «45 татуировок продавана»
- Клиент — с большой буквы: уважение и внимание к деталям
- Мы — продавцы радости: продаём не работу, а облегчение, результат и спокойствие
- Слишком хороший контакт может снижать вероятность продажи (не путать дружбу и сделку)
- «Дайте попробовать» работает: дать клиенту маленькую победу
- Всегда получать решение (Да/Нет/Срок), а не просто информацию
- Невыставленный счёт не может быть оплачен: доп должен быть оформлен и доведён до счёта
- Результат — последовательное выполнение скучных процессов
- Меняем мышление: вместо «почему нельзя» — «как можно продать/упаковать ценность»

- Еженедельные 1:1 CPO–PM по единому шаблону (статус → риски → допработы → что нужно от CPO)
- Файл Plan/Fact по T&M: план часов / факт / отклонения / прогноз до завершения
- Бэклог доппродаж по каждому клиенту (5–10 идей)
- CR-light для изменений скоупа
- Upsell pipeline со статусами

**Q2 (июнь–август):** Стандартизация delivery + автономность PM-ов
- PM-scorecard по 4 показателям
- 2–3 обучения для PM: оценка, управление скоупом, коммуникации
- Упаковать 1–2 услуги в прайс/пакеты

**Q3 (сентябрь–ноябрь):** Рост выручки через клиентов + продуктирование услуг
- 2–3 кейса/отзыва от клиентов
- QBR (квартальный обзор ценности) с ключевыми клиентами
- Retention ключевых клиентов = 100%

**Q4 (декабрь–февраль):** Управление производством как P&L-юнитом (уровень 3)
- Прогноз загрузки на 12 недель (capacity planning)
- Система грейдов для PM и ключевых ролей
- Мотивация PM: привязка бонуса к марже / качеству / CSAT
- Годовой review + план следующего года

**Ритм управления (cadence):**
| Активность | Частота |
|---|---|
| 1:1 CPO–PM | Еженедельно |
| Портфельный обзор (зел/жёлт/красн) | Еженедельно |
| Upsell review (pipeline) | Еженедельно |
| Sprint planning / Next Sprint Menu | Каждый спринт |
| Контроль маржи (plan/fact) | Еженедельно |
| QBR (обзор ценности с клиентом) | Ежеквартально |
